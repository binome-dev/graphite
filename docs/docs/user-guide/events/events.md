# Events System

The Graphite events system records what assistants, workflows, nodes, tools and topics do, as events in an [event store](event_store.md). Events give observability and an audit trail, and they are the record a workflow is recovered from.

## Overview

Events are plain pydantic models, built around a hierarchy where:

- **Base Event**: Provides the fields every event has
- **Category Events**: Bases for component events (Assistant, Node, Tool, Workflow) and topic events
- **Specific Events**: Concrete classes for specific actions (Invoke, Respond, Failed; Publish, Consume)

## Base Event Class

All events inherit from `Event` (`grafi.common.events.event`).

### Fields

| Field            | Type            | Description                                                                 |
|------------------|-----------------|-----------------------------------------------------------------------------|
| `event_id`       | `EventId`       | Unique identifier for the event (generated by default).                     |
| `event_version`  | `int`           | The revision of the event's stored form: `2` (`EVENT_VERSION`).             |
| `invoke_context` | `InvokeContext` | The request the event belongs to.                                           |
| `event_type`     | `EventType`     | The kind of event. Each concrete class accepts only its own.                |
| `timestamp`      | `datetime`      | When the event was created, in UTC (generated by default).                  |

Events have no `to_dict()` or `from_dict()`: an event is saved as its JSON form, and an `EventCodec` reads it back (see [Serialization and Deserialization](#serialization-and-deserialization)).

### Event Types

The `EventType` enumeration defines the built-in event types:

#### Component Events

- `NODE_INVOKE`, `NODE_RESPOND`, `NODE_FAILED`
- `TOOL_INVOKE`, `TOOL_RESPOND`, `TOOL_FAILED`
- `WORKFLOW_INVOKE`, `WORKFLOW_RESPOND`, `WORKFLOW_FAILED`
- `ASSISTANT_INVOKE`, `ASSISTANT_RESPOND`, `ASSISTANT_FAILED`

#### Topic Events

- `TOPIC_EVENT`
- `PUBLISH_TO_TOPIC`, `CONSUME_FROM_TOPIC`

A class with an event type of its own holds only that type: a `ToolInvokeEvent` given `event_type="NodeInvoke"`, in code or in a stored event, fails validation.

## Component Events

Assistants, workflows, nodes and tools each record an invoke event when called, a respond event when they finish, and a failed event when they fail. The classes are in `grafi.common.events.component_events`.

### Common Fields

| Field        | Type  | Description                                          |
|--------------|-------|------------------------------------------------------|
| `id`         | `str` | The component's id.                                  |
| `name`       | `str` | The component's name.                                |
| `type`       | `str` | The component's type.                                |
| `input_data` | (see below) | What the component was given.                  |

Respond events add `output_data`, what the component produced. Failed events add `error` (`str`), the error as text, and `error_details` (`Optional[Dict[str, Any]]`), its structured details when they were captured.

### Events by Component

| Component | Classes | Extra fields | `input_data` | `output_data` |
|-----------|---------|--------------|--------------|---------------|
| Assistant | `AssistantInvokeEvent`, `AssistantRespondEvent`, `AssistantFailedEvent` | | `PublishToTopicEvent` | `List[ConsumeFromTopicEvent]` |
| Workflow | `WorkflowInvokeEvent`, `WorkflowRespondEvent`, `WorkflowFailedEvent` | | `PublishToTopicEvent` | `List[ConsumeFromTopicEvent]` |
| Node | `NodeInvokeEvent`, `NodeRespondEvent`, `NodeFailedEvent` | `subscribed_topics`, `publish_to_topics`: `List[str]` | `List[ConsumeFromTopicEvent]` | `Optional[PublishToTopicEvent]`: the node's publication, or `None` if it published nothing |
| Tool | `ToolInvokeEvent`, `ToolRespondEvent`, `ToolFailedEvent` | | `Messages` | `Messages` |

## Topic Events

Topic events handle message passing between components. These are the primary events used for component interaction.

### TopicEvent (Base Class)

Basic event for topic-related activities.

#### TopicEvent Fields (Extended from Event)

| Field    | Type            | Description                          |
|----------|-----------------|--------------------------------------|
| `name`   | `str`           | Name of the topic.                   |
| `type`   | `TopicType`     | Type of the topic.                   |
| `offset` | `int`           | Position of the event in the topic.  |
| `data`   | `List[Message]` | The messages the event carries.      |

### PublishToTopicEvent

The event recorded when data is published to a topic. This is the output format for nodes and the input format for workflows and assistants.

#### PublishToTopicEvent Fields (Extended from TopicEvent)

| Field                | Type                | Description                                                                    |
|----------------------|---------------------|--------------------------------------------------------------------------------|
| `publisher_name`     | `str`               | Name of the component publishing the data.                                     |
| `publisher_type`     | `str`               | Type of the component publishing the data.                                     |
| `consumed_event_ids` | `List[str]`         | IDs of the events consumed before publishing.                                  |
| `emission_id`        | `Optional[EventId]` | ID of the event a topic copied this publication from (see `prepare_publication()`); `None` on a publication no topic copied, such as the input given to a workflow or a node's output as it emits it, which invoke and respond events record, and in older records. |

### ConsumeFromTopicEvent

The event recorded when data is consumed from a topic. This is the input format for nodes and the output format for workflows and assistants.

#### ConsumeFromTopicEvent Fields (Extended from TopicEvent)

| Field           | Type  | Description                                  |
|-----------------|-------|----------------------------------------------|
| `consumer_name` | `str` | Name of the component consuming the data.    |
| `consumer_type` | `str` | Type of the component consuming the data.    |

## Event Usage Patterns

### Creating Events

```python
from grafi.common.events.component_events import ToolInvokeEvent
from grafi.common.models.invoke_context import InvokeContext
from grafi.common.models.message import Message

# Create invoke context
context = InvokeContext(
    conversation_id="conv_1",
    invoke_id="inv_1",
    assistant_request_id="req_123",
)

# Create tool invoke event
event = ToolInvokeEvent(
    invoke_context=context,
    name="OpenAITool",
    type="OpenAITool",
    input_data=[Message(role="user", content="Hello")],
)
```

### Serialization and Deserialization

An event is stored as its JSON form, `model_dump(mode="json")`: its fields, flat, with `"event_version": 2`. A topic event's `data` is a list of message objects, and a component event holds the events in its `input_data` and `output_data` in the same form. A publication, for example (its message's null fields left out):

```json
{
  "event_id": "evt-1",
  "event_version": 2,
  "invoke_context": {
    "conversation_id": "conv-1",
    "invoke_id": "inv-1",
    "assistant_request_id": "req-1",
    "user_id": "",
    "kwargs": {}
  },
  "event_type": "PublishToTopic",
  "timestamp": "2026-10-20T09:30:00Z",
  "name": "agent_input_topic",
  "type": "AgentInputTopic",
  "offset": 0,
  "data": [
    {"message_id": "m-1", "timestamp": 1, "content": "Hello", "role": "user"}
  ],
  "emission_id": null,
  "consumed_event_ids": [],
  "publisher_name": "Assistant",
  "publisher_type": "Assistant"
}
```

An event in a field typed as one of its base classes is saved as its own class, with all of its fields. `Message.tools` is a list (tools given as a generator are read into one), so a message saves the same each time.

An `EventCodec` (`grafi.common.events.event_codec`) encodes and decodes this form. `default_event_codec` knows every built-in event type, and the event stores use it:

```python
import json

from grafi.common.events.event_codec import default_event_codec

stored = default_event_codec.encode(event)  # A dict of JSON values.
text = json.dumps(stored)

same = default_event_codec.decode(json.loads(text))  # A ToolInvokeEvent.
assert same == event
```

`decode` chooses the class by `event_type`.

#### Errors

An event store is the record a workflow is recovered from, so the codec never skips an event. Both methods raise `EventSerializationError` (`grafi.common.exceptions`), with the cause chained:

- `encode`, for an event holding a value JSON cannot hold, or of a class other than the one its `event_type` decodes as (an unregistered class, or a subclass), as it could not be read back.
- `decode`, for a stored event that is not a JSON object, has an unknown `event_type`, has a missing or unknown `event_version` or one newer than this grafi's, or does not validate as its class.

#### Version 1 Events

Events stored before version 2 have `"event_version": "1.0"`. They kept the component's or topic's fields and the invoke context under `event_context`, a topic event's messages as JSON text in `data`, and a component event's input, output and error under `data`. `decode` upgrades such an event of grafi's own types, and the events nested in it, to version 2 before validating it (`grafi.common.events.event_v1.upcast_v1`), so events already stored need no migration. That covers grafi 0.0.25 and later, 0.0.25 having named some fields otherwise (`topic_name`, `node_id`, `input_event`); an event of an earlier grafi raises `EventSerializationError`.

#### Custom Event Types

An event type of your own is decoded once its class is registered:

```python
from grafi.common.events.event import Event
from grafi.common.events.event_codec import default_event_codec


class AuditEvent(Event):
    event_type: str = "Audit"  # type: ignore[assignment]
    note: str


default_event_codec.register("Audit", AuditEvent)
```

`default_event_codec` is shared by every store in the process; see [Event Reconstruction](event_store.md#event-reconstruction) for a registry of a store's own.

An event of yours is stored as `model_dump(mode="json")`: its `to_dict()` and
`from_dict()` are never called now, and a `UserWarning` says so where they are
written. An event of your own that grafi 0.0.36 or earlier stored with your `to_dict()`,
of version 1 (`"event_version": "1.0"`), reaches its class as stored: grafi
upgrades version 1 of its own event types only, so one of yours stored in
grafi's layout can call `grafi.common.events.event_v1.upcast_v1(data)` there.
From version 2 on, every event, yours included, is upgraded alike. The stored
event must carry its `event_version`, as 0.0.36's `Event.event_dict()` wrote
it: one without it raises `EventSerializationError` ("has version None"). Read
it in a `model_validator(mode="before")`, which returns the fields this
grafi's `Event` has (version 2's today, as `upcast_v1` gives them):

```python
from typing import Any

from pydantic import model_validator


class AuditEvent(Event):
    event_type: str = "Audit"  # type: ignore[assignment]
    note: str

    @model_validator(mode="before")
    @classmethod
    def _read_v1(cls, data: Any) -> Any:
        if isinstance(data, dict) and data.get("event_version") == "1.0":
            data = {  # The layout its to_dict() wrote.
                "event_id": data["event_id"],
                "timestamp": data["timestamp"],
                "invoke_context": data["context"],
                "note": data["payload"]["note"],
            }
        return data
```

## Event Context and Metadata

### InvokeContext

All events carry an `InvokeContext` that provides:

- **Request Tracking**: `conversation_id`, `invoke_id`, `assistant_request_id` and `user_id` for correlating related events
- **Metadata**: `kwargs`, additional context passed through the workflow

`kwargs` is saved with each event as JSON, so its values must be JSON values: strings, numbers, booleans, `None`, and lists and dicts of them. A few others are converted: a datetime is saved as its ISO text, a tuple as a list. An event read back holds the JSON value, the datetime's text rather than a datetime. A value JSON cannot hold, such as an arbitrary object, is refused when the `InvokeContext` is made: pydantic's `ValidationError` names its key.

## Best Practices

### Event Design

1. **Immutability**: Events should be immutable once created
2. **Complete Information**: Include all relevant context for debugging and monitoring
3. **Structured Data**: Use typed fields rather than generic data blobs
4. **Correlation**: Ensure proper `invoke_context` for request correlation

### Event Handling Best Practices

1. **Type Safety**: Use `isinstance()` checks for type-specific handling
2. **Error Handling**: Expect `EventSerializationError` from a store's reads: an event it cannot decode is never skipped
3. **Logging**: Log important events for debugging and monitoring
4. **Performance**: Avoid expensive operations in event handlers

### Serialization

1. **JSON Compatibility**: Keep event data, `invoke_context.kwargs` included, to JSON values
2. **Schema Versioning**: `event_version` names the stored form; decoding upgrades an older version of grafi's own event types, and of yours from version 2 on (version 1 of yours reaches its class as stored)
3. **Registration**: Register custom event types before reading a store that holds them
4. **Testing**: Use `EventStoreInMemory(strict=True)` in tests, so events pass through JSON as in a durable store

### Topic Event Best Practices

1. **Event Correlation**: Use `consumed_event_ids` to track event dependencies
2. **Publisher Information**: Always include `publisher_name` and `publisher_type` for traceability
3. **Offset Management**: Properly manage topic offsets for ordered processing

## Integration with Graphite

### Observability

Events integrate with Graphite's observability system:

- **Tracing**: Events can be correlated with OpenInference traces
- **Monitoring**: Event streams provide real-time system monitoring
- **Debugging**: Event history helps diagnose issues

### Workflow Coordination

Events enable loose coupling between workflow components:

- **Asynchronous Processing**: Components can react to events asynchronously
- **Topic-Based Communication**: Events flow through topic-based messaging
- **State Management**: Events provide a history of state changes

### Error Handling

Failed events provide structured error information:

- **Error Details**: `error` holds the error's text, and `error_details` its structured details
- **Context Preservation**: Failed events retain full context for debugging
- **Recovery Strategies**: Error events can trigger recovery mechanisms

### Event Sourcing

The events system supports event sourcing patterns:

- **Event History**: Complete history of system state changes
- **Replay Capability**: Events can be replayed to reconstruct system state
- **Audit Trail**: Events provide a complete audit trail of operations

The events system forms the backbone of Graphite's event-driven architecture, enabling robust, observable, and loosely-coupled systems that can scale and adapt to complex workflow requirements.
